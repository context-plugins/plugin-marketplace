# Getting started with an APIMatic-generated TypeScript SDK

This is the **SDK-specific** reference and grounding layer, and the entry into the companion
`typescript-*` skills. These SDKs are produced by **APIMATIC v3.0** (every generated file carries a
`This file was automatically generated by APIMATIC v3.0` header) and are built on the shared
`@apimatic/*` runtime packages (`@apimatic/core`, `@apimatic/schema`, `@apimatic/axios-client-adapter`,
`@apimatic/authentication-adapters`, and `@apimatic/oauth-adapters` when the API uses OAuth). For the
general patterns that apply to *any* such SDK (client setup, auth, calling endpoints, models, error
handling, retries, testing), see the companion API-agnostic skills: `typescript-client-initialization`,
`typescript-authentication`, `typescript-calling-endpoints`, `typescript-models`,
`typescript-error-handling`, `typescript-configuration-resilience`, `typescript-testing`.

**The source and these companion skills are complementary — load both.** The generated source is
authoritative for the SDK's *surface* (the `Client` constructor, the `Configuration` interface,
controller method signatures, model interfaces and their schemas, which error type an operation throws);
the companion skills are the *usage layer* on top — the right way to call each piece and the gotchas a
signature can't show. Reading the source doesn't remove the need to load the skill for that step, so at
each step below load the companion *and* confirm names against the source.

> **Before writing any integration code, clone the SDK source** (one command, in the *SDK source* section
> below) and read it to confirm every signature, interface, enum, schema, and error type as you go. Do
> **not** copy the SDK source into your project, and do **not** fetch GitHub files ad hoc — clone once,
> then grep the local copy. It's a throwaway reference: delete it when the integration is done.

## SDK identity

| | |
| --- | --- |
| API | `api.apis.guru` |
| Generator | APIMATIC v3.0 (`automatically generated by APIMATIC v3.0` header on every file) |
| Runtime dependencies | `@apimatic/core`, `@apimatic/schema`, `@apimatic/axios-client-adapter`, `@apimatic/authentication-adapters` (+ `@apimatic/oauth-adapters` only when the API uses OAuth) — see `package.json` `dependencies` |
| npm package id | the `"name"` in `package.json` (e.g. `multiauth-samplelib`, `apimatic-calculatorlib`) — per-API |
| Install | `npm install "https://github.com/context-plugins/api-apis-guru-typescript-013bf4#main"` |
| Client | a single exported `Client` class, constructed with `new Client(config?: Partial<Configuration>)` |
| Configuration | a plain `Configuration` **options object** (interface in `src/configuration.ts`), passed to the constructor; all fields optional via `Partial` |
| Auth | nested credential objects on the `Configuration` (e.g. `basicAuthCredentials`, `oAuthCCGCredentials`) — see **typescript-authentication** |
| Environment | a `enum Environment` in `src/configuration.ts` (e.g. `Environment.Production`, `Environment.Testing`) — names/default per-API |
| Controllers | `{Resource}Controller` classes you instantiate: `new {Resource}Controller(client)` — **not** accessors on the client |
| Return type | every operation returns `Promise<ApiResponse<T>>` (paginated ops return `PagedAsyncIterable<...>`) |

| Node version | per `package.json` `engines.node` (these SDKs target `>=14.17.0`) |
| Module format | dual ESM/CJS (`exports` map + `main`/`module`/`typings` in `package.json`); ships TypeScript types |

The table above is **orientation, not a copy-paste recipe** — it gives you the names and facts (package
id, `Client`/`Configuration`, the auth *pattern*, the environments), while the actual integration code
comes from the companion skills. Load each one as you reach its step (see **Integration workflow** below)
and confirm its types against the cloned source.

## Package layout

APIMatic TypeScript SDKs live under `src/`, with everything re-exported from `src/index.ts`:

- `src/client.ts` — the `Client` class (`constructor(config?: Partial<Configuration>)`, `withConfiguration`,
  static `fromJsonConfig` / `fromEnvironment`, and the private base-URL resolver). OAuth-using SDKs expose
  public OAuth managers (e.g. `oAuthCCGManager`) here.
- `src/configuration.ts` — the `Configuration` interface (timeout, environment, credential objects,
  `httpClientOptions`), the `Environment` enum, and the env/JSON config readers.
- `src/defaultConfiguration.ts` — `DEFAULT_CONFIGURATION` and `DEFAULT_RETRY_CONFIG` (the actual defaults).
- `src/controllers/` — one `{Resource}Controller` per API resource group, each extending `BaseController`.
- `src/models/` — request/response **interfaces**, each paired with a `{name}Schema` for runtime
  (de)serialization; `src/models/containers/` for oneOf/anyOf union types. **This is where field names,
  optionality, and enum values live.**
- `src/errors/` — typed error subclasses (`class {Name}Error extends ApiError<{Payload}>`), when the API
  documents error responses.
- `src/core.ts` and `src/clientAdapter.ts` — thin re-exports of the runtime (`@apimatic/core`,
  `@apimatic/axios-client-adapter`); this is where `ApiError`, `ApiResponse`, `RetryConfiguration`,
  `HttpClientOptions`, `RequestOptions` actually come from.
- `src/schema.ts` — re-export of `@apimatic/schema` (the `object`/`optional`/`oneOf`/… combinators).

## Install

```bash
npm install "https://github.com/context-plugins/api-apis-guru-typescript-013bf4#main"
```

```ts
import { Client, Environment, ApiError } from 'points-of-interestlib';
// controllers and model types are also exported from the package root:
import { {Resource}Controller } from 'points-of-interestlib';
```

Everything public is re-exported from `src/index.ts`, so import names come from the **package root** — you
don't import from subpaths. `npm install` pulls the `@apimatic/*` runtime packages transitively.

## SDK source — clone it first; don't fetch files ad hoc

You will constantly need to confirm real constructor/method signatures, model interfaces, schemas, enum
values, and error types, and the **only reliable way** is to read the SDK source. Clone it once, up front
— before writing integration code — into your **system temp directory** (outside your project), then read
and grep the local copy. It is a read-only, throwaway reference:

```bash
# Linux / macOS:
git clone --depth 1 --branch main https://github.com/context-plugins/api-apis-guru-typescript-013bf4 /tmp/api-apis-guru-typescript-src
```

```powershell
# Windows (PowerShell):
git clone --depth 1 --branch main https://github.com/context-plugins/api-apis-guru-typescript-013bf4 "$env:TEMP\api-apis-guru-typescript-src"
```

Then confirm the SDK shape **only** from that local clone:

- **Don't fetch GitHub files one at a time** — `…/blob/…` pages return HTML and guessed paths fail. Clone
  once and read locally. Only if `git` is unavailable, fetch a **raw** URL of the form
  `https://raw.githubusercontent.com/{owner}/{repo}/{branch}/…` (never a `…/blob/…` page).

Layout — grep the clone here first:

- `package.json` — the npm `name`, `version`, `engines.node`, and the `@apimatic/*` `dependencies`.
- `src/configuration.ts` — the `Configuration` fields, the `Environment` enum, and the env-var names in
  `fromEnvironment`.
- `src/client.ts` — the `Client` constructor and (for OAuth) the manager properties.
- `src/controllers/*.ts` — operation methods and their `Promise<ApiResponse<T>>` signatures.
- `src/models/` — request/response interfaces, enums, and `containers/` unions; **this is where field
  names live**.
- `src/errors/` — typed error subclasses (when generated).
- `README.md` and `doc/` — a generated, human-readable index: `doc/client.md`, `doc/auth/*.md`,
  `doc/controllers/*.md`, `doc/models/*.md`, `doc/http-client-options.md`, `doc/retry-configuration.md`,
  `doc/api-response.md`, `doc/api-error.md`, `doc/environment-based-client-initialization.md`,
  `doc/configuration-based-client-initialization.md`. **Grep `doc/` first** — it is the fastest way to
  find an operation, its parameters, and a copy-pasteable usage snippet, then open the `.ts` file for the
  exact signature.

Clean up when done:

```bash
rm -rf /tmp/api-apis-guru-typescript-src                               # Linux / macOS
```
```powershell
Remove-Item -Recurse -Force "$env:TEMP\api-apis-guru-typescript-src"   # Windows
```

## Integration workflow — load the companion skill at each step

Before you write the code for each step, load the named companion skill — even if you've already read the
relevant source. Each step calls out the trap the signature hides (in *parens*).

1. **Client construction** — load **typescript-client-initialization** before you call
   `new Client({...})`. (*The signature won't tell you:* the client is configured with a single
   `Partial<Configuration>` options object — there is no separate options/builder; `httpClientOptions`
   nests timeout/retries/proxy/agents; create one client and reuse it.)
2. **Authentication** — load **typescript-authentication** before you set credentials. (*The signature
   won't tell you:* each scheme is a **nested credential object** on the `Configuration`
   (`basicAuthCredentials`, `apiKeyCredentials`, `oAuthCCGCredentials`, …), not a single token string; set
   it at construction and load secrets from the environment.)
3. **Calling an endpoint** — load **typescript-calling-endpoints** before the first call. (*The signature
   won't tell you:* you **instantiate the controller yourself** — `new {Resource}Controller(client)` — the
   client exposes no controller accessors; methods are `async`, parameters are passed positionally **or**
   bundled in a single destructured `{ ... }` object, and the return is `ApiResponse<T>`, not the bare
   value.)
4. **Models** — load **typescript-models** the moment a request/response field isn't a plain string or
   number. (*The signature won't tell you:* models are plain **interfaces** validated by a paired runtime
   schema; optional fields are `?`; oneOf/anyOf are TS union types `A | B` built as plain object literals
   and read with `is{Variant}` type-guards; enums are TS `enum`s; unknown JSON is preserved only on
   `expandoObject` models.)
5. **Error handling** — load **typescript-error-handling** before your first `try/catch`. (*The signature
   won't tell you:* a non-2xx **throws** `ApiError` (or a typed subclass in `src/errors/`) carrying
   `.statusCode`/`.result`/`.body`/`.headers`; abort and schema-validation throw *different* error types.)
6. **Configuration & resilience** — load **typescript-configuration-resilience** when you tune retries,
   timeouts, transport, or the base URL. (*The signature won't tell you:* retries are **disabled by
   default** (`maxNumberOfRetries` = 0) and only `GET`/`PUT` are retried even when enabled; everything
   tunable lives under `httpClientOptions`.)
7. **Testing** — load **typescript-testing** before you stub the SDK. (*The signature won't tell you:* the
   test seam is a custom `HttpClientInterface` (via `unstable_httpClientOptions`), not a base-URL
   override; no SDK mocking helpers ship for consumers.)
